# OptimalSnow

Computes the optimal placement of **k snow deposit sites** for a city, given a total snow volume **V** and a set of candidate deposit locations. Each road segment is assigned to its nearest open deposit, subject to capacity constraints.

The problem is formulated as a **capacitated p-median**, solved with [OR-Tools](https://developers.google.com/optimization/) (CP-SAT or CBC).

---

## How it works

```
User inputs: total snow volume V, number of depots k, solver
                        ↓
     Compute snow demand per road: proportional to road area
                        ↓
     Cluster roads into spatial demand zones (KMeans)
                        ↓
     Solve capacitated p-median on cluster representatives
                        ↓
     Map cluster assignments back to individual streets
                        ↓
     Output: selected deposit sites + street assignment (GeoJSON)
```

### Problem formulation

- **Decision variables**: which k deposits to open; which deposit each road cluster is assigned to
- **Objective**: minimize total weighted travel distance (snow volume × distance to assigned deposit)
- **Constraints**: each cluster assigned to exactly one open deposit; deposit capacity not exceeded

```
OptimalSnow/

│   └── solvers/
│       ├── __init__.py      # Unified solver interface

├── data_prepared/<city>/    # Generated by prepare_data.py (not tracked in git)

```

## Setup

**Python 3.11** recommended. Install dependencies:

```bash
pip install geopandas pandas numpy osmnx networkx scikit-learn pyarrow
pip install "ortools==9.11.*" "protobuf>=5.26,<6.0"
```

> **Note for macOS (Apple Silicon):** ortools 9.14+ has a protobuf compatibility issue. Use ortools 9.11 with protobuf 5.x as shown above.

## Usage

### Step 1 — Preprocess data (run once per city)

```bash
python src/prepare_data.py --city tallinn
```

This downloads the city's OSM road network, computes the full road-to-deposit distance matrix, and saves everything to `data_prepared/<city>/`. The distance matrix step can take several minutes.

**Input data required** (paths configured per city in `src/city_config.py`), e.g. for Tallinn in `data/tallinn/`:
- `tallinn_roads.geojson` — road segments with an `area_sqm` column
- `snow_capacity_municipality.geojson` — municipal deposit candidates with `snow_capacity_m3`
- `snow_capacity_government.geojson` — government deposit candidates with `snow_capacity_m3`

To add a city, put its input files under `data/<city>/` and add a `CityConfig` entry in `src/city_config.py`.

### Step 2 — Run the solver

Start the API:

```bash
uvicorn main:app --port 8000
```

Then submit a job with the total snow volume (`tsv`, m³), the number of deposits to open (`p`), the solver (`"cpsat"` or `"cbc"`) and the city:

```bash
curl -X POST localhost:8000/jobs/ -H "Content-Type: application/json" \
  -d '{"tsv": 1000000, "p": 5, "solver": "cpsat", "city_name": "tallinn"}'
```

Poll `GET /jobs/{job_id}/status` and download the results with `GET /jobs/{job_id}/download-results`.

When running with Docker Compose, the host folder `.data_prepared/` is mounted as `data_prepared/` in the container, so put the preprocessed data in `.data_prepared/<city>/`.

### Web map

Open the API root (e.g. `http://localhost:8000/`) in a browser. The side panel takes the city, snow volume, number of sites and solver, warns when the volume exceeds what the chosen number of sites can hold, and follows the job. The map then shows the selected sites (sized by capacity) and colours every street by the site it is assigned to; click a site in the list to highlight its streets. The URL (`#job=<id>`) can be reopened while the server keeps the job in memory.

The page uses these endpoints, which return GeoJSON in EPSG:4326:

| Endpoint | Returns |
|----------|---------|
| `GET /cities` | Available cities, map bounds, and the max capacity for each number of sites |
| `GET /cities/{city}/deposits` | Candidate deposit sites (points) with capacities |
| `GET /jobs/{id}/deposits` | Selected sites with capacity, assigned snow and number of streets |
| `GET /jobs/{id}/streets` | Streets with assigned site and snow volume |

### Outputs

Two GeoJSON files are written to `outputs/<job_id>/` (the download endpoint renames them to `selected_deposits.geojson` and `roads_with_clusters.geojson` inside the zip):

| File | Contents |
|------|----------|
| `results_deposits.geojson` | Selected deposit sites with all original attributes + `deposit_index` |
| `results_street_assignment.geojson` | All road segments with `assigned_deposit_index` and `cluster_id` |

`assigned_deposit_index` in the street file matches `deposit_index` in the deposits file.

## Solver options

| Method | Flag | Notes |
|--------|------|-------|
| CP-SAT | `"cpsat"` | Recommended. Parallel search, handles large instances well. Use `K=100` allowed depots per cluster. |
| CBC (MILP) | `"cbc"` | Exact MILP solver. Slower on large instances. Use `K=20` allowed depots per cluster. |

When using CBC, consider lowering `K` in `src/main.py`:
```python
allowed_indices = build_allowed_assignments_cluster(cluster_dist_matrix, K=20)
```

---

## API integration

`main.py` wraps `src.main.run_pipeline` in a FastAPI service. The only per-job inputs are `tsv`, `p`, `solver` and `city_name`; the preprocessed data in `data_prepared/<city>/` is shared across all jobs for that city. Jobs are kept in memory, so they are lost when the server restarts.
